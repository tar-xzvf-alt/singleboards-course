# Как Linux управляет железом: от записи в файл до мигания LED

## 1. Вступление: где заканчивается программа и начинается железо? · 0–10 мин

Покажите модуль, плату Dock и два управляемых LED. Оранжевый индикатор
питания отдельно отметьте как неуправляемый программно.

**Реплика преподавателя:**

> Сегодня мы не будем учиться писать циклы. Мы попробуем понять,
> почему обычная программа способна управлять физическим устройством.
> Начнём с самой простой команды и постепенно раскроем, что за ней стоит.

Спросите: **«Если я отправлю текст через UART, кто будет включать LED:
мой ноутбук, Python на плате или Linux?»** Соберите несколько версий,
пока не исправляя все формулировки. К этому вопросу вернитесь в конце.

Кратко определите аппаратные термины:

- **SoC** — микросхема с процессорным ядром и контроллерами периферии.
- **GPIO** — управляемый цифровой контакт. На выходе он задаёт низкий
  или высокий электрический уровень.
- **Контроллер** — аппаратный блок, который выполняет определённую операцию:
  например, управляет GPIO или передаёт последовательность битов.

Настройки контроллеров хранятся в аппаратных **регистрах** — небольших
ячейках состояния микросхемы. Драйвер знает, как с ними работать;
приложению LED class не нужно знать их адреса и назначение отдельных битов.

Наш зелёный LED подключён к PC1: буква C означает банк контактов,
число 1 — контакт внутри банка. Это не номер вывода разъёма Dock.
При active high высокий уровень включает LED. RGB подключён к PC0,
но получает последовательность данных, а не просто команду «подать единицу».

## 2. Пять участников одной операции · 10–25 мин

Нарисуйте схему и оставьте её видимой на всё занятие:

```text
Пользовательское пространство               Пространство ядра          Оборудование

терминал или Python ── системный вызов ──→ sysfs / LED class
                                                │
                                                ↓
                                           драйвер LED
                                                │
                                                ↓
                                        GPIO-драйвер или LEDC ──→ контроллер ──→ LED
```

### Программа

Программа решает, **что и когда** сделать: включить LED, подождать,
выключить. Она работает в пользовательском пространстве — обычном
окружении процессов. Python не знает адресов регистров D1 из самой
операции записи в файл.

### Ядро и системный вызов

Ядро Linux управляет процессами, памятью и доступом к устройствам.
Процесс обращается к его услугам через **системные вызовы**:
`open`/`openat`, `read`, `write`, `close` и другие.

Объяснение без деталей процессорных режимов:

> Программа просит открыть определённый путь и передать туда данные.
> Ядро проверяет доступ, определяет, что это за объект, и вызывает нужный
> обработчик. Само по себе наличие прав root не превращает Python в драйвер.

### Драйвер

**Драйвер** — код ядра, который знает способ управления устройством.
Приложение сообщает желаемую яркость, а драйвер выполняет аппаратные
операции. LED class даёт приложениям общий интерфейс, хотя разные
светодиоды могут быть подключены к GPIO, I²C-контроллеру или LEDC.

Для PC1 цепочка проходит через `gpio-leds` и GPIO-драйвер.
Для RGB используется `leds-sun50i-a100` и аппаратный контроллер LEDC.
Ядро и драйвер не обязательно меняют железо прямо внутри `write`:
работа может выполняться через очередь или завершаться по прерыванию.

### Библиотека

**Библиотека** — готовый код, который использует программа. Она может
скрывать открытие файлов, проверку значений и обработку ошибок.
Позже мы покажем конкретную библиотеку, которая обращается к тому же sysfs.

**Вопрос:** «Если заменить Python на C, исчезнет ли драйвер?»
**Ожидаемый ответ:** нет; изменится язык программы, а интерфейс ядра
и путь к оборудованию могут остаться теми же.

## 3. Откуда Linux знает, что PC1 — это светодиод? · 25–35 мин

На SoC есть много контактов, и один контакт часто имеет несколько функций.
По наличию PC1 ядро не может угадать, что производитель подключил к нему LED.

**Device Tree** — описание оборудования и его соединений.
Файл DTS читаем человеком, DTB — его скомпилированная форма,
которую загрузчик передаёт ядру вместе с Image. Device Tree не является
программой мигания и не выполняет циклы.

Покажите только короткий фрагмент, а не весь DTS:

```dts
leds {
    compatible = "gpio-leds";
    led-0 {
        color = <LED_COLOR_ID_GREEN>;
        function = LED_FUNCTION_STATUS;
        gpios = <&pio 2 1 GPIO_ACTIVE_HIGH>; /* PC1 */
    };
};
```

Объясните четыре факта:

1. `compatible` позволяет сопоставить устройство с подходящим драйвером.
2. `gpios` указывает GPIO-контроллер, банк C (2), контакт 1 и полярность.
3. Цвет и назначение участвуют в формировании имени `green:status`.
4. При наличии включённого драйвера ядро регистрирует LED и создаёт интерфейс.

```text
DTS → компиляция → DTB → загрузчик → ядро → драйвер → /sys/class/leds/green:status
```

Выполните:

```bash
cat /proc/device-tree/model
ls -l /sys/class/leds
readlink -f /sys/class/leds/green:status
```

Символическая ссылка связывает удобный каталог класса с конкретным
устройством: это путь, указывающий на другой путь, а не второе устройство.
На нашем стенде зелёный LED уже был описан в DTS модуля.
Для RGB мы добавили LEDC и переключение PC0 в функцию `ledc`.

**Вопрос:** «Что будет, если драйвер есть, но описание LED в DT отсутствует?»
**Ответ:** для этого подключения драйвер не получит нужного описания,
поэтому ожидаемый LED может не появиться. Нужны и описание, и драйвер.

## 4. Почему запись в файл включает LED? · 35–50 мин

### Сначала прочитаем свойства

```bash
ls /sys/class/leds/green:status
cat /sys/class/leds/green:status/max_brightness
cat /sys/class/leds/green:status/brightness
cat /sys/class/leds/green:status/trigger
```

**sysfs** — виртуальная файловая система, в которой ядро показывает
устройства и их свойства. `/sys/class/leds` объединяет устройства LED class.
Это не каталог текстовых настроек на SD-карте: чтение и запись атрибутов
вызывают обработчики ядра.

`brightness` задаёт состояние/яркость, `max_brightness` сообщает верхнюю
границу, `trigger` выбирает источник автоматического управления.
В списке trigger текущий выбор заключён в квадратные скобки.
У зелёного LED максимум 1: это управление включением, а не плавная регулировка.

### Одна запись — одно изменение состояния

Перед запуском попросите студентов предсказать результат:

```bash
echo none > /sys/class/leds/green:status/trigger
echo 1 > /sys/class/leds/green:status/brightness
cat /sys/class/leds/green:status/brightness
echo 0 > /sys/class/leds/green:status/brightness
```

`>` означает перенаправление вывода команды в открытый файл.
Shell открывает путь, `echo` передаёт текст `1` с переводом строки,
ядро разбирает значение и передаёт запрос LED-подсистеме.
Драйвер задаёт уровень GPIO, ток проходит через цепь светодиода — появляется свет.

**Реплика преподавателя:**

> Мы не записали единицу на SD-карту. Мы использовали файловую операцию
> как способ передать команду устройству. Похожий вид интерфейса
> не означает одинаковое устройство обычного файла и атрибута sysfs.

После `echo 1` процесс команды уже завершился, но LED остаётся включённым.
Состояние оборудования не обязано исчезать вместе с программой.

### Пять миганий из простой программы

Покажите [`green_sysfs.py`](lesson_examples/green_sysfs.py):

```python
from pathlib import Path
from time import sleep

led = Path("/sys/class/leds/green:status")
maximum = led.joinpath("max_brightness").read_text().strip()
led.joinpath("trigger").write_text("none\n")

try:
    for _ in range(5):
        led.joinpath("brightness").write_text(maximum + "\n")
        sleep(0.5)
        led.joinpath("brightness").write_text("0\n")
        sleep(0.5)
except KeyboardInterrupt:
    pass
finally:
    led.joinpath("brightness").write_text("0\n")
```

Запустите:

```bash
python3 green_sysfs.py
```

Разберите только смысл строк: путь устройства, чтение максимума, пять
повторений, две записи и две паузы. `write_text` открывает файл,
пишет и закрывает его; эта удобная операция тоже приводит к системным вызовам.
`finally` выключает LED при обычном завершении и Ctrl-C.
`KeyboardInterrupt` — уведомление Python о Ctrl-C, а `pass` здесь означает
«закончить без дополнительного действия»; очистка всё равно выполняется.

Короткие учебные примеры не обрабатывают SIGTERM и SIGKILL.
По умолчанию SIGTERM может завершить процесс без выполнения `finally`,
а SIGKILL не позволяет выполнить очистку вообще. Для показа используйте
обычное завершение или Ctrl-C. Более универсальные примеры находятся рядом
в родительском каталоге и отдельно обрабатывают SIGTERM.

**Вопрос:** «Кто отсчитывает полсекунды в этом варианте?»
**Ответ:** пользовательский процесс задаёт паузы и время следующей записи;
ядро планирует его выполнение. `sleep` не гарантирует точный момент
возобновления, поэтому это подход для видимого мигания, а не точного протокола.

## 5. Программа закончилась, а LED продолжает мигать · 50–60 мин

**Trigger** — источник событий LED внутри ядра. `timer` позволяет поручить
ему периодическое мигание. Для GPIO LED этого стенда это программный
таймер ядра, а не автономная аппаратная схема мигания.

Спросите до запуска: «Сейчас мы не запускаем бесконечный Python-цикл.
Сможет ли LED продолжать мигать?»

```bash
echo timer > /sys/class/leds/green:status/trigger
echo 500 > /sys/class/leds/green:status/delay_on
echo 500 > /sys/class/leds/green:status/delay_off
cat /sys/class/leds/green:status/trigger
```

`delay_on` и `delay_off` измеряются **в миллисекундах** и появляются
после выбора trigger `timer`. Команды завершаются, приглашение терминала
возвращается, а LED продолжает мигать. Запустите `uname -r` или другую
короткую команду, пока студенты наблюдают LED.

Сравните два случая:

| Вариант | Кто определяет момент переключения | Нужен продолжающий работать процесс Python |
|---|---|---|
| Цикл с `sleep` | Программа в пользовательском пространстве | Да |
| Trigger `timer` | Таймер LED-подсистемы ядра | Нет |

Trigger тоже не обещает идеальной точности реального времени.
Его преимущество здесь — перенос стандартного поведения в ядро.
Остановите мигание перед следующим примером:

```bash
echo none > /sys/class/leds/green:status/trigger
echo 0 > /sys/class/leds/green:status/brightness
```

## 6. Что меняет библиотека? · 60–70 мин

Покажите [`green_library.py`](lesson_examples/green_library.py):

```python
from pathlib import Path
from time import sleep
from periphery import LED

Path("/sys/class/leds/green:status/trigger").write_text("none\n")

with LED("green:status") as led:
    try:
        for _ in range(5):
            led.write(True)
            sleep(0.5)
            led.write(False)
            sleep(0.5)
    except KeyboardInterrupt:
        pass
    finally:
        led.write(False)
```

```bash
python3 green_library.py
```

`True` означает включение до `max_brightness`, `False` — ноль.
Библиотека читает максимум, открывает `brightness`, проверяет значения,
записывает их через `os.write` и возвращает позицию файлового дескриптора
к началу. **Файловый дескриптор** — номер открытого ресурса, выданный ядром
процессу; следующие операции используют этот номер.
`with` обеспечивает закрытие ресурса; **закрытие не выключает LED**,
поэтому явный `led.write(False)` в `finally` всё ещё нужен.
Trigger отключаем отдельно: класс `LED` этой библиотеки им не управляет.

```text
Прямой путь:    программа → файловые операции → sysfs → драйвер → LED
С библиотекой:  программа → periphery.LED → файловые операции → sysfs → драйвер → LED
```

Библиотека улучшает интерфейс программы и повторно использует готовый код.
Она не убирает проверки прав ядром и не создаёт отсутствующий драйвер.
Не все библиотеки используют sysfs: эта схема описывает именно `periphery.LED`.

### Почему здесь не используем libgpiod

Для свободных GPIO современный интерфейс Linux — `/dev/gpiochip*`;
`libgpiod` работает с ним через файловые дескрипторы и ioctl.
На нашей плате PC1 уже запрошен драйвером `gpio-leds`. Приложение не должно
параллельно запрашивать эту линию как свободный GPIO: получит конфликт владения.

| Что требуется приложению | Подходящий интерфейс |
|---|---|
| Управлять зарегистрированным LED | LED class; sysfs напрямую или библиотека LED |
| Управлять свободным GPIO | GPIO character device; например, libgpiod |
| Обмениваться данными с устройством I²C или SPI | Соответствующий интерфейс шины и библиотека |

**Важно:** устаревший GPIO sysfs `/sys/class/gpio` и используемый здесь
LED sysfs `/sys/class/leds` — разные интерфейсы. Устаревание первого
не означает, что демонстрация LED class использует тот же старый GPIO API.

**Вопрос:** «Можно ли библиотекой обойти отсутствие прав на устройство?»
**Ответ:** нет. Она обращается к тому же интерфейсу ядра от имени процесса.

## 7. RGB: один интерфейс, другое оборудование · 70–82 мин

RGB LED содержит красный, зелёный и синий каналы. У WS2812 есть своя
управляющая схема: цвет передаётся последовательностью битов по одному
сигнальному проводу. Подать постоянную единицу на PC0 для выбора цвета недостаточно.

Посмотрите свойства:

```bash
cat /sys/class/leds/rgb:status/max_brightness
cat /sys/class/leds/rgb:status/multi_index
cat /sys/class/leds/rgb:status/multi_intensity
```

`multi_index` объявляет порядок компонент. Для стенда это `red green blue`.
`multi_intensity` задаёт пропорции цвета, а `brightness` — общую яркость.
При максимуме 255 драйвер рассчитывает канал примерно как:

```text
яркость канала = общая яркость × интенсивность канала / 255
```

Для `255 0 0` и общей яркости 31 красный канал получает 31,
а зелёный и синий — ноль. Для `255 255 255` включены все три канала;
это белый в нашей демонстрации, а не обещание точной цветовой калибровки.

Покажите [`rgb_sysfs.py`](lesson_examples/rgb_sysfs.py):

```python
from pathlib import Path
from time import sleep

led = Path("/sys/class/leds/rgb:status")
assert led.joinpath("multi_index").read_text().split() == ["red", "green", "blue"]
led.joinpath("trigger").write_text("none\n")
led.joinpath("brightness").write_text("0\n")

try:
    for color in ("255 0 0", "0 255 0", "0 0 255", "255 255 255"):
        print(color, flush=True)
        led.joinpath("multi_intensity").write_text(color + "\n")
        led.joinpath("brightness").write_text("31\n")
        sleep(1)
except KeyboardInterrupt:
    pass
finally:
    led.joinpath("brightness").write_text("0\n")
```

```bash
python3 rgb_sysfs.py
```

Четыре цвета держатся по секунде, чтобы аудитория успела их увидеть.
`assert` здесь останавливает пример при неожиданном порядке компонент;
не запускайте этот учебный пример с `python3 -O`, отключающим такие проверки.
В обычных приложениях используют явную проверку и преобразование порядка,
как в более универсальном `rgb_led.py` родительского каталога.

Нарисуйте вторую аппаратную цепочку:

```text
Python → LED multicolor → драйвер LEDC → FIFO → аппаратные импульсы на PC0 → WS2812
```

Именно LEDC формирует короткие импульсы передачи битов, а Python лишь
редко задаёт новый цвет. GRB на проводе настраивается в DTS и контроллере;
это не порядок значений в проверенном `multi_index`.
Прерывание сообщает драйверу о завершении передачи. При желании покажите
увеличение счётчика до и после нового запуска:

```bash
grep -i led /proc/interrupts
python3 rgb_sysfs.py
grep -i led /proc/interrupts
```

Класс `LED` библиотеки `python-periphery` управляет общей `brightness`,
но не предоставляет API для `multi_intensity`. Для цвета здесь используем sysfs.
Высокоуровневая библиотека может обернуть и его; возможности конкретного
класса нужно проверять, а не выводить из названия библиотеки.

**Вопрос:** «Почему можем менять цвет из Python, но не хотим формировать
из Python каждый импульс WS2812?»
**Ответ:** выбор цвета не требует микросекундной точности;
передача битов требует точных импульсов, которые создаёт аппаратный контроллер.

## 8. Обсуждение: восстановим цепочку · 82–90 мин

Попросите участников отвечать по схеме на доске. Не требуйте терминов
наизусть: сначала принять объяснение своими словами, затем уточнить название.

| Ситуация или вопрос | Ожидаемое объяснение |
|---|---|
| LED отсутствует в `/sys/class/leds`. Поможет ли другой цикл Python? | Сначала проверить описание платы и драйвер; цикл не создаёт устройство |
| При записи получили `Permission denied` | Запрос дошёл до интерфейса, но процесс не имеет нужных прав |
| Команда `echo 1` закончилась, LED горит | Состояние устройства сохраняется; процесс не нужен для удержания состояния |
| После команд настройки LED сам мигает | Trigger `timer` выполняет работу в ядре |
| Переписали программу на C. Где теперь драйвер? | По-прежнему в ядре; язык приложения не определяет аппаратный интерфейс |
| Библиотечный объект закрыли. Должен ли LED погаснуть? | Не обязательно; закрытие ресурса и изменение состояния — разные операции |
| RGB показывает неожиданные цвета | Проверить `multi_index`, значения компонент и настройку порядка на проводе |
| Можно ли просто запросить PC1 через libgpiod? | Линия занята `gpio-leds`; нужен правильный интерфейс и единый владелец |

Вернитесь к исходному вопросу о UART. Совместно сформулируйте итог:

> Ноутбук передаёт команду терминалу платы. Процесс на плате обращается
> к ядру через системный вызов. Ядро вызывает драйвер, драйвер управляет
> контроллером, а контроллер изменяет электрический сигнал.
> Библиотека делает обращение удобнее, Device Tree описывает соединения.

```bash
echo none > /sys/class/leds/green:status/trigger
echo 0 > /sys/class/leds/green:status/brightness
echo none > /sys/class/leds/rgb:status/trigger
echo 0 > /sys/class/leds/rgb:status/brightness
```

## Дополнительный показ: увидеть системные вызовы

Если есть время или вопрос «где доказательство, что библиотека пишет файл?»:

```bash
strace -f -yy -e trace=openat,write,lseek,close -o /tmp/green-sysfs.trace \
  python3 green_sysfs.py
grep 'green:status' /tmp/green-sysfs.trace

strace -f -yy -e trace=openat,write,lseek,close -o /tmp/green-library.trace \
  python3 green_library.py
grep 'green:status' /tmp/green-library.trace
```

`strace` наблюдает системные вызовы процесса; `-yy` подписывает пути
у файловых дескрипторов. В обоих выводах видны обращения к `brightness`
и записи `1\n`/`0\n`. В прямом примере файл открывается для каждой записи;
библиотека сохраняет открытый дескриптор и использует `lseek`.
Числа дескрипторов и точный вывод могут отличаться между запусками.
Фильтруем по имени LED: после разрешения символической ссылки `strace`
может подписывать дескриптор полным путём `/sys/devices/...`, а не
исходным `/sys/class/leds/...`.

Пример реально наблюдавшихся строк, сокращённый для показа:

```text
write(3</sys/devices/platform/leds/leds/green:status/brightness>, "1\n", 2) = 2
write(3</sys/devices/platform/leds/leds/green:status/brightness>, "0\n", 2) = 2
```

Здесь 3 — дескриптор, 2 — число записанных байтов: цифра и перевод строки.
Никаких адресов аппаратных регистров в запросе приложения нет.

Показывайте несколько строк, а не весь запуск Python. Это средство
наблюдения границы между приложением и ядром, не трассировка электрического
сигнала. Для формы импульсов нужен другой инструмент — осциллограф
или логический анализатор.

## Если демонстрация не сработала

| Признак | Что проверяет преподаватель |
|---|---|
| Нет каталога LED | `uname -r`, модель DT, включение драйверов, журнал загрузки |
| LED меняется сам | Выбранный `trigger`, другие запущенные LED-программы |
| Нет `delay_on`/`delay_off` | Сначала выбрать `timer` и проверить список доступных trigger |
| `ModuleNotFoundError: periphery` | Выбор Python/venv или наличие wheel в `PYTHONPATH` текущей сессии |
| `AssertionError` в RGB | `multi_index` отличается от ожидаемого порядка; не отключать проверку ради запуска |
| `Permission denied` | Выполнение на плате и права процесса; не менять права всех устройств |

Команды встречи выполняются из root-сессии. В обычной системе доступ
выдают целевыми правилами и группами. Запись вида `sudo echo 1 > файл`
может не помочь: перенаправление выполняет shell до запуска `sudo`.
Для такой системы используют, например, `echo 1 | sudo tee файл`.
