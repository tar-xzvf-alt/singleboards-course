# Лабораторная №3. Использование кросс-компилятора

## Цель работы

Научиться собирать на компьютере с архитектурой x86-64 программы для RISC-V, проверять их с помощью QEMU и запускать на целевой плате.

## Оборудование и предварительные требования

- рабочий компьютер с ALT Linux на архитектуре x86-64;
- одноплатный компьютер Lichee RV Dock с архитектурой RISC-V;
- настроенное подключение к плате и средство передачи файлов;
- права суперпользователя на рабочем компьютере;
- редактор исходного кода.

## Ключевые понятия

> [!NOTE]
> **Кросс-компиляция** — сборка программы на одной аппаратной или программной платформе для выполнения на другой целевой платформе.

Обычный цикл разработки для целевой архитектуры включает написание кода, сборку кросс-компилятором, перенос программы на плату или запуск в эмуляторе, а затем проверку и отладку.

> [!NOTE]
> **Тулчейн (toolchain)** — набор компиляторов, компоновщиков, библиотек и вспомогательных утилит для разработки под определённую платформу.

Кросс-компилятор в этой работе работает на x86-64, но создаёт программы для RISC-V. В ALT Linux нужные инструменты доступны в пакете `gcc-riscv64-linux-gnu` из [репозитория для разработчиков](https://packages.altlinux.org/en/sisyphus/srpms/cross-toolchain-riscv64-linux-gnu/).

> [!NOTE]
> **QEMU user-mode** — режим эмуляции, в котором программа для гостевой архитектуры выполняется на ядре хостовой Linux с трансляцией инструкций и системных вызовов.

Механизм `binfmt_misc` позволяет ядру Linux распознать исполняемый файл RISC-V и автоматически передать его зарегистрированному интерпретатору QEMU. Это даёт возможность проверить консольную программу на рабочем компьютере до переноса на плату.

## Порядок выполнения

### Проверка среды разработки

Проверьте архитектуру рабочего компьютера, текущую конфигурацию репозиториев и наличие инструментов:

```bash
uname -m
apt-repo
command -v riscv64-linux-gnu-gcc
command -v qemu-riscv64-static
```

> [!CAUTION]
> Не выполняйте `apt-repo rm all` и не переключайте ветку общей рабочей станции ради одной лабораторной. Если пакеты отсутствуют в настроенной ветке, используйте подготовленный преподавателем образ, контейнер или локальный репозиторий.

### Установка инструментов

Если инструменты отсутствуют и нужные пакеты доступны в уже настроенных репозиториях, установите кросс-компилятор и поддержку запуска программ RISC-V через QEMU:

```bash
apt-get install gcc-riscv64-linux-gnu qemu-user-static-binfmt-riscv
```

Для написания программы используйте любой доступный редактор или IDE. В консольной среде можно работать с `vim`, `neovim`, `nano` или `emacs`.

Проверьте доступность компилятора:

```bash
riscv64-linux-gnu-gcc --version
qemu-riscv64-static --version
```

### Подготовка программы

Напишите на C приложение, которое принимает числовой аргумент из командной строки и с помощью математической библиотеки вычисляет пять значений выбранных элементарных функций. Предусмотрите проверку количества аргументов и корректности введённого значения.

Имя исходного файла в следующих командах замените на фактическое.

### Кросс-компиляция

Соберите статически скомпонованный исполняемый файл и подключите математическую библиотеку:

```bash
riscv64-linux-gnu-gcc -O2 -Wall -Wextra -Wpedantic -static -o math-app math-app.c -lm
```

> [!WARNING]
> Для показанного ниже запуска через QEMU нужна статическая компоновка. Без `-static` программе потребуются загрузчик и динамические библиотеки RISC-V, которых по умолчанию нет на рабочем компьютере.

Проверьте архитектуру полученного файла:

```bash
file math-app
riscv64-linux-gnu-readelf -h math-app
```

> [!TIP]
> **Ожидаемый результат.** Утилита `file` должна определить исполняемый файл как 64-разрядный RISC-V ELF и указать статическую компоновку. В выводе `readelf` поле `Machine` должно содержать `RISC-V`.

### Запуск через QEMU

Проверьте регистрацию обработчика RISC-V:

```bash
ls /proc/sys/fs/binfmt_misc/qemu-riscv64
```

При настроенном `binfmt_misc` программу можно запустить как обычный исполняемый файл:

```bash
chmod +x math-app
./math-app аргумент
```

Если автоматический запуск не настроен, вызовите эмулятор явно:

```bash
qemu-riscv64-static ./math-app аргумент
```

> [!TIP]
> **Проверка запуска.** Программа должна вывести пять вычисленных значений и одинаково обрабатывать корректный аргумент при автоматическом и явном запуске через QEMU.

На рисунке показан пример работы приложения, запущенного через QEMU user-mode:

### Запуск на целевой плате

Вычислите контрольную сумму, передайте исполняемый файл на Lichee RV Dock с помощью `scp`, снова вычислите контрольную сумму на плате, выдайте право на выполнение и запустите программу с тем же аргументом. Сравнивайте результаты только после подтверждения, что на хосте и плате находится один файл.

```bash
sha256sum math-app
scp math-app пользователь@IP-адрес_платы:~/
```

На плате, работая через UART или SSH, проверьте и запустите полученный файл:

```bash
sha256sum ~/math-app
chmod +x ~/math-app
~/math-app аргумент
```

## Задание

1. Убедитесь в наличии или установите кросс-компилятор и подходящий редактор на рабочем компьютере.
2. Напишите приложение на C, которое принимает аргумент через интерфейс командной строки и с помощью библиотеки `libm` вычисляет пять значений выбранных элементарных математических функций.
3. Соберите приложение кросс-компилятором для RISC-V со статической компоновкой.
4. Проверьте архитектуру и заголовок ELF исполняемого файла.
5. Запустите программу через QEMU user-mode.
6. Передайте исполняемый файл на плату, подтвердите его контрольную сумму и выполните его.
7. Сравните результаты запуска на рабочем компьютере и плате.
8. Продемонстрируйте преподавателю исходный код, сборку и оба варианта запуска.

## Дополнительные задания

### Вариант 1. Инспектор ELF

Соберите одну программу для двух архитектур и сравните файлы:

```bash
gcc -O2 -Wall -Wextra -Wpedantic -o math-app-x86_64 math-app.c -lm
riscv64-linux-gnu-gcc -O2 -Wall -Wextra -Wpedantic -static -o math-app-riscv64 math-app.c -lm
file math-app-x86_64 math-app-riscv64
riscv64-linux-gnu-readelf -h math-app-riscv64
```

Определите архитектуру, класс ELF, порядок байтов, ABI, тип файла и способ линковки. Докажите архитектуру каждого файла по его содержимому, а не по имени.

### Вариант 2. Надёжный интерфейс командной строки

Доработайте приложение с использованием `strtod`, `errno` и `isfinite`. Оно должно различать отсутствие аргумента, лишние символы после числа, `inf`, значение вне области определения и переполнение математической функции. Для каждой ошибки выведите сообщение в `stderr` и верните отдельный ненулевой код.

Составьте и выполните таблицу тестов как минимум для допустимого значения, отсутствующего аргумента, `abc`, `2x`, `inf`, отрицательного значения и значения, вызывающего переполнение `exp`. Запустите те же тесты через QEMU и на плате.

### Вариант 3. Статическая и динамическая сборки

Соберите два RISC-V-файла и сравните их размер и заголовки:

```bash
riscv64-linux-gnu-gcc -O2 -Wall -Wextra -Wpedantic -static -o math-app-static math-app.c -lm
riscv64-linux-gnu-gcc -O2 -Wall -Wextra -Wpedantic -o math-app-dynamic math-app.c -lm
ls -l math-app-static math-app-dynamic
file math-app-static math-app-dynamic
riscv64-linux-gnu-readelf -l math-app-dynamic
```

Воспроизведите ошибку запуска динамического файла без библиотек целевой архитектуры, затем укажите sysroot явно:

```bash
SYSROOT=$(riscv64-linux-gnu-gcc -print-sysroot)
qemu-riscv64-static ./math-app-dynamic аргумент
qemu-riscv64-static -L "$SYSROOT" ./math-app-dynamic аргумент
```

Передайте оба файла на плату и проверьте их запуск. Объясните различие в размере и требованиях к окружению.

### Вариант 4. Воспроизводимая сборка

Создайте `Makefile` с переменными `CC`, `CFLAGS` и `LDLIBS`, целями `all`, `math-app-static`, `math-app-dynamic` и `clean`. Объявите `all` и `clean` фиктивными целями через `.PHONY`.

Дважды выполните чистую сборку и сравните результаты:

```bash
make clean all
sha256sum math-app-static math-app-dynamic > hashes-1.txt
make clean all
sha256sum math-app-static math-app-dynamic > hashes-2.txt
diff -u hashes-1.txt hashes-2.txt
```

Команда `make clean` должна удалять только артефакты этого проекта. Объясните результат сравнения хешей.

### Вариант 5. Системные вызовы под QEMU

Запустите статическую программу с трассировкой, сохранив системные вызовы отдельно от обычного вывода:

```bash
qemu-riscv64-static -strace ./math-app-static аргумент 2> trace.log
```

Найдите в журнале как минимум `write` и `exit_group`, свяжите их с действиями программы и объясните отличие системного вызова от машинной инструкции. После оформления результата удалите журнал.

### Вариант 6. Численная сопоставимость

Сначала подтвердите, что на рабочем компьютере и плате находится один RISC-V-файл, сравнив его SHA-256. Для входов `0`, `0.5`, `2` и `10` сохраните вывод и код возврата при запуске через QEMU и непосредственно на Lichee RV Dock.

Сравните результаты с помощью `diff`. Если строки различаются только последними разрядами, вычислите абсолютное или относительное отклонение и обоснуйте допустимую погрешность. В отчёте приведите таблицу «вход — QEMU — Lichee — код возврата — результат сравнения». Удалите переданный бинарник и временные результаты.
