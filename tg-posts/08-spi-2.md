**SPI: тестирование и spidev. Часть 2/2**

После того как включили SPI в Device Tree и ядре, в `/dev/` должен появиться `spidev1.0` (или `spidev1.1` — зависит от того, как прописали в DT). Через него можно общаться с периферией из userspace на Python:

```python
import spidev
spi = spidev.SpiDev()
spi.open(1, 0)           # шина 1, устройство 0
spi.max_speed_hz = 1000000
response = spi.xfer2([0xAA, 0xFF])  # отправить и прочитать ответ
```

`xfer2()` сама управляет CS: опускает перед передачей и поднимает после. Это критично для протоколов, где CS используется как синхронизирующий сигнал, например при обмене с Arduino в режиме SPI-slave.

Самый простой тест — замкнуть MOSI на MISO проводом. Отправляешь байт и тут же читаешь его обратно:

```python
spi.xfer2([0xA5])  # вернёт [0xA5]
```

Если вернулся 0x00 или 0xFF — что-то не так с подключением или конфигурацией. Если 0xA5 — SPI жив и можно подключать реальные устройства.

Типичные грабли: забыли включить DMA_SUN6I (без него SPI_SUN6I не инициализируется), не прописали spidev в Device Tree (контроллер есть, а символьного устройства нет), перепутали режим CPOL/CPHA (данные есть, но мусор).

Логический анализатор тут — лучший друг. Подключил к CS, SCK, MOSI, MISO — и сразу видно, на каком этапе проблема.
