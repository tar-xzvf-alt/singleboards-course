# Реестр дополнительных заданий

Этот документ содержит дополнительные задания, которые рассматриваются для включения в лабораторные работы. Он не импортируется в методичку и используется для разработки, стендовой проверки и фиксации результатов.

Задание переносится в текст лабораторной только после полного прогона на целевом стенде. До этого в соответствующей лабораторной сохраняется только заголовок «Дополнительные задания».

## Статусы проверки

| Статус | Значение |
|---|---|
| **Не проверено** | Задание сформулировано, но команды и полный сценарий на стенде не выполнялись. |
| **Проверены команды** | Основные команды или отдельные этапы работают, но полный студенческий сценарий и его длительность не проверены. |
| **Проверено полностью** | Задание выполнено от начала до конца на целевом стенде, зафиксированы время, результат и очистка после эксперимента. |
| **Требует исправления** | Во время проверки обнаружен блокер, неоднозначность или превышение допустимого времени. |

Для статуса «Проверено полностью» обязательны:

- модель платы, версия образа и используемое оборудование;
- точная последовательность действий без скрытых подготовительных шагов;
- фактический результат и критерий успешности;
- продолжительность выполнения студентом или проверяющим;
- минимум одна типовая ошибка и способ восстановления;
- подтверждение, что после задания не остались процессы, пользователи, ключи или изменённые настройки.

## Лабораторная №1

### 1.1. Карта загрузки

**Идея:** запустить `tio` с временными метками и записью журнала, перезагрузить плату и найти в журнале работу загрузчика, запуск ядра Linux и запуск пользовательского пространства.

```bash
tio -b 115200 -t -L --log-file boot.log /dev/ttyUSBX
```

**Ожидаемый результат:** для каждого из трёх этапов приведена характерная строка и объяснено, что к этому моменту уже работает.

**Текущий статус:** проверены команды.

**Что проверено:** `tio 3.9` поддерживает параметры `-t`, `-L` и `--log-file`; UART открывается на скорости 115200 после предоставления пользователю группы `uucp`.

**Что осталось:** выполнить штатную перезагрузку, проверить полноту `boot.log`, подобрать устойчивые признаки трёх этапов и измерить время задания.

### 1.2. Паспорт платы

**Идея:** составить таблицу с архитектурой, числом процессоров, версией ядра, RAM, разделами, файловыми системами, сетью, именем системы и часовым поясом.

**Ожидаемый результат:** для каждого значения указаны команда, фактическое значение и краткая интерпретация.

**Текущий статус:** проверены команды.

**Что проверено:** на стенде работают `lscpu`, `free -h`, `lsblk -f`, `ip -brief address`, `hostnamectl` и `timedatectl`. Подтверждены `riscv64`, один CPU, 472 МиБ RAM, разделы BOOT/ROOTFS и интерфейс `wlan0`.

**Что осталось:** пройти сценарий по студенческой формулировке, оценить понятность таблицы и измерить время оформления.

### 1.3. Сравнение Lichee и рабочего компьютера

**Идея:** выполнить `uname -a`, `lscpu`, `free -h`, `lsblk -f` и `ip -brief address` на обеих системах, затем объяснить не менее пяти различий.

**Ожидаемый результат:** различия разделены на архитектурные, ресурсные и связанные с назначением системы.

**Текущий статус:** проверены команды.

**Что проверено:** команды доступны на Lichee и рабочем компьютере; на Lichee подтверждена архитектура `riscv64`.

**Что осталось:** выполнить полное сравнение, проверить достижимость пяти содержательных различий и измерить время анализа.

### 1.4. Устойчивое имя UART

**Идея:** определить модель и серийный номер USB-UART-преобразователя и сравнить `/dev/ttyUSBX` с путём из `/dev/serial/by-id/`.

```bash
udevadm info --query=property --name=/dev/ttyUSBX
ls -l /dev/serial/by-id/
```

**Ожидаемый результат:** студент объясняет, почему символьная ссылка по идентификатору устойчивее динамического номера `ttyUSBX`.

**Текущий статус:** проверены команды.

**Что проверено:** обе команды выполнены на рабочем компьютере; адаптер FT232R имеет путь в `/dev/serial/by-id/`, указывающий на `/dev/ttyUSB0`.

**Что осталось:** измерить время выполнения студентом и проверить сценарий с двумя адаптерами, если он будет заявлен в критериях.

### 1.5. Наблюдение нагрузки

**Идея:** запустить один контролируемый вычислительный процесс, найти его в `top`, зафиксировать нагрузку, корректно завершить и подтвердить возврат системы в исходное состояние.

**Ожидаемый результат:** известны PID, команда завершения, загрузка до/во время/после опыта; фонового процесса не осталось.

**Текущий статус:** не проверено.

**План проверки:** выбрать команду, доступную в базовом образе без установки пакетов; ограничить длительность; проверить остановку по PID и нагрузку на однопроцессорном D1.

### 1.6. Диагностика неверной скорости

**Идея:** подключиться к UART со скоростью, отличной от 115200 бод, наблюдать загрузку, зафиксировать искажённый вывод и восстановить правильные параметры.

**Ожидаемый результат:** студент изменяет только скорость и объясняет, почему нечитаемые символы подтверждают наличие электрического сигнала.

**Текущий статус:** не проверено.

**План проверки:** выбрать заведомо неверную скорость, выполнить перезагрузку, убедиться в воспроизводимом симптоме, вернуть 115200 и проверить отсутствие побочных изменений.

## Лабораторная №2

### 2.1. Карта сетевого пути

**Идея:** изобразить путь от рабочего компьютера до Lichee через точку доступа и подписать интерфейсы, IPv4-адреса, префикс и шлюз.

**Ожидаемый результат:** каждое значение подтверждено выводом `ip -brief address` или `ip route` на соответствующей системе.

**Текущий статус:** проверены команды.

**Что проверено:** Lichee получает IPv4 по Wi-Fi, имеет маршрут по умолчанию, видит шлюз, разрешает DNS-имя и доступна с рабочего компьютера.

**Что осталось:** оформить полную карту с обеих сторон и проверить, укладывается ли объяснение младшекурсника в отведённое время.

### 2.2. Двусторонняя передача

**Идея:** передать текстовый и бинарный файлы на Lichee, проверить размер и SHA-256, изменить текстовый файл и вернуть его под новым именем.

**Ожидаемый результат:** исходные копии имеют одинаковые хеши, а изменённый удалённый файл получает новый хеш.

**Текущий статус:** проверены команды.

**Что проверено:** SCP работает в обе стороны; файл передан на Lichee, SHA-256 на рабочем компьютере и плате совпал; обратное копирование также выполнено.

**Что осталось:** пройти буквально сценарий с двумя типами файлов, удалённым изменением, тремя контрольными суммами, очисткой и замером времени.

### 2.3. Псевдоним SSH

**Идея:** создать запись `Host lichee-team` в `~/.ssh/config`, указав `HostName`, `User` и `IdentityFile`, затем подключиться по псевдониму.

**Ожидаемый результат:** `ssh lichee-team` использует нужного пользователя и ключ без отключения проверки ключа сервера.

**Текущий статус:** не проверено.

**План проверки:** создать отдельный временный конфигурационный файл через `ssh -F`, чтобы не изменять пользовательский `~/.ssh/config`; после успешного теста проверить основной учебный сценарий и очистку.

### 2.4. Удалённая команда

**Идея:** без интерактивного входа получить имя пользователя, версию ядра, архитектуру и доступную память, сохранив вывод на рабочем компьютере.

**Ожидаемый результат:** студент объясняет, где исполнялись команды и какой shell выполнял перенаправление в файл.

**Текущий статус:** проверены команды.

**Что проверено:** вход по ключу с `BatchMode=yes` работает; удалённые `whoami`, `pwd` и системные команды выполняются.

**Что осталось:** проверить точную составную команду, локальное перенаправление, содержимое файла и время выполнения.

### 2.5. SSH-туннель

**Идея:** запустить на Lichee HTTP-сервис, привязанный к `127.0.0.1:8000`, и открыть его с рабочего компьютера через локальный порт 8080.

```bash
python3 -m http.server 8000 --bind 127.0.0.1
ssh -L 8080:127.0.0.1:8000 пользователь@IP-адрес_платы
```

**Ожидаемый результат:** страница недоступна напрямую по адресу платы, но доступна через `http://127.0.0.1:8080`; после проверки оба процесса завершены.

**Текущий статус:** проверены команды.

**Что проверено:** Python 3.13 присутствует; HTTP-сервис и SSH-туннель запускаются без ошибки.

**Что осталось:** подтвердить HTTP-запрос через туннель, проверить отсутствие прямого доступа, завершить оба процесса штатно и измерить время задания.

### 2.6. Диагностика соединения

**Идея:** найти одну обратимую неисправность: неверного пользователя или IP-адрес, остановленный `sshd`, ошибку DNS либо неправильные права `authorized_keys`.

**Ожидаемый результат:** оформлен протокол «симптом → гипотеза → команда проверки → результат → исправление»; изменяется по одному фактору за раз.

**Текущий статус:** не проверено.

**План проверки:** подготовить отдельную карточку и процедуру восстановления для каждого отказа; проверить, что остановка `sshd` выполняется только при открытом UART; для прав ключа использовать временного пользователя.

## Зафиксированные результаты основной части

Следующие результаты относятся к обязательной части лабораторных и не повышают статус дополнительных заданий автоматически:

- `ssh-copy-id` успешно проверен для отдельного пользователя с домашним каталогом;
- вход по ключу подтверждён с `BatchMode=yes`;
- после `ssh-copy-id` каталог `.ssh` имел режим `700`, а `authorized_keys` — `600`;
- временный пользователь и его домашний каталог удалены после проверки;
- `sshd -t`, `systemctl is-active sshd` и проверка TCP-порта 22 прошли успешно;
- на образе отсутствует `fdisk`, поэтому в лабораторной №1 используется `lsblk -f`;
- исходный каталог `/root` отсутствовал, из-за чего первая попытка `ssh-copy-id` для root дала ложное сообщение об успехе; каталог был создан с режимом `700`, после чего вход по ключу проверен.
